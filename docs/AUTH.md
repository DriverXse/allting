# Authentication setup

Production users authenticate through AllTing's own email flow. Firebase handles
passwords and verification/reset delivery; Better Auth issues AllTing sessions in
D1. Passwords are never stored by AllTing. No service-account file is required.

## Firebase email and password (recommended)

1. Create a **new Firebase project that you own** in the Firebase console.
2. Register a Web app. Copy its `projectId` and `apiKey` privately; no Analytics
   initialization, Firestore or Firebase Storage is needed.
3. Open Authentication, enable **Email/Password** under Sign-in method.
4. Under Authentication settings, add your exact production hostname to
   Authorized domains. Enter only the hostname, without `https://` or a path.
   Use the generated Sites or workers.dev hostname if you have no owned domain.
5. Configure your host with `ALLTING_AUTH_METHOD=password`, your
   `FIREBASE_PROJECT_ID`, secret `FIREBASE_API_KEY`, secret `BETTER_AUTH_SECRET`,
   and exact `ALLTING_ORIGIN`. Publish to apply these settings.
6. Register a disposable account using an email inbox you control. Follow the
   verification email, log in, finish onboarding and check password reset.
   Delete or rotate disposable credentials before general launch.

Do not enable anonymous accounts or treat a client claim as email verification.
The server checks project identity, subject and verified email with Firebase.
Refresh credentials are encrypted per session and rechecked periodically;
password reset and provider suspension invalidate older sessions at the next check.
Keep `BETTER_AUTH_SECRET` stable; rotating it invalidates existing sessions.

## Alternative production magic links

Set `ALLTING_AUTH_METHOD=magic-link`. Configure a sending-only `RESEND_API_KEY`
and `AUTH_EMAIL_FROM`, using an address on your own verified sender domain.
Configure the exact HTTPS origin and a fresh session secret. A generated hosting
domain alone does not supply a verified email sender domain.
Tokens expire after 15 minutes, are stored hashed, can be consumed once, and are
submitted only after the visitor confirms sign-in. Emails and raw links must not
be logged. Do not switch a working production installation's auth method without
the owner's explicit decision and verification of account continuity.

## Local testing

`npm run setup:local` selects the loopback-only magic-link mailbox by default.
For local password tests, use a separate Firebase Authentication emulator on
`http://127.0.0.1:9099`, project `demo-allting`. Set `.dev.vars` to:

```dotenv
ALLTING_AUTH_METHOD=password
FIREBASE_PROJECT_ID=demo-allting
FIREBASE_API_KEY=demo-allting-key
FIREBASE_AUTH_EMULATOR=http://127.0.0.1:9099
```

`demo-allting-key` is a nonfunctional emulator fixture, not a real API key.
Keep the random `BETTER_AUTH_SECRET` generated by local setup. Never set the
emulator variable in production. Unit tests do not need a running emulator.

## Moderation access

Set the host's private `ADMIN_EMAIL` to one exact verified AllTing account address.
Publish again, then refresh that account's profile: **Moderering** links to
`/admin`. Firebase-project ownership alone does not confer AllTing privileges.
An existing internal domain-user ID may alternatively be authorized by
`ADMIN_USER_ID`; this is not a Firebase UID. Prefer `ADMIN_EMAIL` for initial setup.
Never set a default admin in public source or trust a role sent by the browser.
Admin and moderator share one privilege level in version 1.

For multiple staff, roles may be assigned through a tightly controlled database
operation by an authorized operator; there is no invitation or role-management UI.
Removing an environment allowlist entry alone may not revoke a stored `admin`
role. Check both allowlist settings and the user's stored role during revocation.
Only explicitly reported messages are available to moderators, not arbitrary chats.
